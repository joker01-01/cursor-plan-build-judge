# 规划 → 执行 → 验收

在复杂任务中使用显式三阶段工作流：

1. **Planner（规划）** — 把需求变成可执行、可验收的规格
2. **Builder（执行）** — 严格按规格实现，不偷改范围
3. **Judge（验收）** — 基于真实产物与验收标准判定通过/不通过

## 何时使用

- 多步骤任务
- 需求模糊或不完整
- 有明确或可推导的验收标准
- 跨文件 / 跨模块改动
- 应该先规划再实现的工作
- 脚本、文档、配置、分析等可检查产物

## 何时不要使用

- 简单问答
- 一行级小改动
- 用户明确要求一步直出
- 规划成本明显高于收益的情况

## 默认交互方式

默认顺序：

1. 只完成 **Planner**
2. 停住，等待用户确认或补充
3. 获得放行后再进入 **Builder**
4. 然后进入 **Judge**

Planner 之后，以下回复可视为放行：

- 继续 / OK / LGTM / go / build
- 按这个做 / 开始实现
- 其他等价的简短确认

若用户在确认时修改了部分规格，以修改后的规格为准继续。

若用户明确要求一口气跑完三阶段，可以连续执行，但输出必须清楚分成三个阶段。

除非用户明确要求跳过审查，否则 Builder 之后不要跳过 Judge。

## 阶段 A：Planner

理解用户需求，改写为可执行规格。

必须输出：

- **目标**
- **输入**
- **输出**
- **约束**
- **假设**
- **边界情况**
- **验收标准**
- **给 Builder 的执行提示**

规则：

- 本阶段不要直接实现最终结果，除非用户明确要求一步直出或连续跑完三阶段。
- 优先结构化输出。
- 低影响歧义可主动给合理默认，并写进「假设」。
- 只有会显著改变范围、风险或成败标准的高影响歧义，才需要先问用户。
- 「给 Builder 的执行提示」要具体到另一人/另一代理也能不回看原需求就能执行。

## 阶段 B：Builder

严格按 Planner 规格执行（包含用户确认时改过的内容）。

规则：

- 不擅自扩大或缩小范围
- 不忽略约束
- 如需新增假设，必须先说明再继续
- 不添加未请求的功能、重构或顺手清理
- 只产出被要求的结果
- 尽量让验收标准易于核查（清晰的文件、命令、输出）

## 阶段 C：Judge

对照以下三项审查 Builder 结果：

1. 原始用户需求
2. Planner 规格（含已确认修改）
3. 验收标准

规则：

- 除非用户明确要求修改，否则不要直接重写结果
- 不得仅依据 Builder 的摘要、自评或「已完成」声明下结论
- 优先基于实际证据：文件、代码 diff、命令输出、日志、测试结果或其他可验证产物
- 若证据不足，明确写出哪些项无法核实，并视为审查缺口

必须输出：

- **结论**：通过 / 不通过
- **问题列表**
- **严重程度**（每个问题）：高 / 中 / 低
- **修改建议**
- **是否需要返工**：是 / 否

若结论为「不通过」，到此停止。不要自动打回 Builder 返工，等待用户决定是否继续修改。

## 证据标准

Judge 应依据模型摘要之外的真实产物，例如：

- 仓库文件与 diff
- 终端输出
- 测试或 lint 结果
- 可检查内容的生成文档

「做完了」「都满足了」这类表述本身不是证据。

## 与 User Rule 的关系

本 Skill 是完整、可分享的工作流版本。个人 User Rule 仍可用简短提醒，让复杂任务默认走「规划 → 执行 → 验收」。两者同时存在时，实际执行以本 Skill 的阶段约定为准。
